## 1. ทำไมต้องมี

CMG คืนสินค้าจากลูกค้าหลายแบบ: เคาน์เตอร์ consign ใน Central/Robinson, Brand Shop, temp shop, local mall และงาน Promotion เช่น Biggest Sale **[เจ้าของ]** แต่ละแบบมีเลขคุมของตัวเองหลายเลข (MIM, RTV Note ของห้าง, SAP Document No., SD10, ใบแจ้งเก็บ, TK ใน Sprint FC, Matdoc, เลข CN) **[ข้อมูล]** แต่ละฝ่ายจึงพูดถึงงานเดียวกันด้วยเลขคนละเลข และไม่มีใครเห็นภาพตั้งแต่ต้นจนจบ

Demo นี้มีไว้ให้ผู้บริหารและทุก role เห็นว่า ถ้ามี **เลข RTV เดียว** ที่ระบบออกให้ตอนเปิดคำสั่ง และทุกคนทำงานบนเลขนั้น งานจะตามได้ตั้งแต่เปิดคำสั่งจนออก CN แล้วส่งต่อให้ทีม dev ของ Central พัฒนาเป็นระบบจริง

## 2. เป้าหมาย

**ต้องมี [เจ้าของ]**
1. Track & trace: ทุกขั้นมีเวลาและผู้ทำ ดู timeline ได้จากเลข RTV
2. One RTV: เลขที่ระบบออกเป็นเลขหลัก ทุก role ใช้เลขเดียวกัน เลขเอกสารอื่นอยู่ใต้เลขนี้

**สิ่งที่ต้องส่งมอบ [เจ้าของ]**
1. Flow คร่าวๆ: ใครทำอะไร
2. Flow ละเอียด และ walkthrough ในแอป
3. Demo ทุก role ทีละขั้นแบบดูง่าย

**ไม่ทำในรอบนี้**
- ไม่มี backend, ฐานข้อมูล, login จริง หรือการเชื่อม SAP / Sprint FC / MIM / JDA
- ไม่มีข้อมูลจริงของร้าน คนขับ หรือพนักงาน (ใช้ข้อมูลสมมติทั้งหมด)
- ไม่ครอบคลุมขาออกหลัง CN (put away, product select, ส่งกลับสาขา) — แสดงเป็น "ระยะถัดไป" ในหน้า flow เท่านั้น
- ไม่แทนที่แอป pickup เดิมใน `C:\Workbench\CMG_Transport_DP` และไม่กระทบแผน UAT ของแอปนั้น

**จะถือว่าล้มเหลวถ้า**
- คนดูต้องอ่านคู่มือก่อนจึงจะเข้าใจ demo
- แต่ละ role ยังเห็นเลขหลักไม่เหมือนกัน
- Demo ทำให้เข้าใจว่าระบบเชื่อม SAP แล้ว ทั้งที่ยังไม่ได้เชื่อม

## 3. เลข One RTV

- รูปแบบ **[ผมเลือก]**: `RTV-CMG-YYMM-NNNNN` เช่น `RTV-CMG-2611-00042` (BU + ปีเดือน + ลำดับ) ออกทันทีที่ Brand/ฝ่ายขายกดเปิดคำสั่ง
- เลขของห้างเรียกว่า **"RTV Note (ห้าง)"** ทุกที่ในแอป เพื่อไม่ให้สับสนกับเลขหลัก **[ผมเลือก]**
- 1 RTV = 1 สาขาต้นทาง + 1 แบรนด์ + 1 ประเภทการคืน มีได้หลายกล่อง แต่ละกล่องมีเลขกล่อง `…-B01`, `-B02` **[ผมเลือก]**
- เอกสารอ้างอิงใต้เลข RTV (กรอกเพิ่มได้เมื่อถึงขั้นนั้น):

| เอกสาร | มาจาก | ใครกรอก |
|---|---|---|
| MIM (26xxxxxx) | SAP/MIM | Brand / PC |
| RTV Note (ห้าง) | JDA ของห้าง | Brand / PC (เฉพาะ consign) |
| SD10 / RTV Form | เอกสารหน้าร้าน | Brand / PC |
| ใบแจ้งเก็บ | ระบบนี้ออกให้ | CS |
| BDC / GIC Slip, เลขพัสดุ | ขนส่ง | ขนส่ง |
| TK | Sprint FC | คลัง CMG |
| Matdoc / เลข 104… / SAP Document No. | SAP | Admin CN |
| CN | SAP | Admin CN |

- ช่องค้นหาเดียว: พิมพ์เลขใดก็ได้ในตารางนี้ แล้วระบบพาไปที่เลข RTV หลัก

### 5.2 ประเภทการคืนเปลี่ยน flow อย่างไร

ประเภทการคืนมี 2 แกน: **ช่องทาง** (Consign / Shop / Temp shop / Local mall) และ **Normal หรือ Promotion** **[ข้อมูล]**

|---|---|---|---|
| Consign (Central/Robinson) | CG Network (GIC) ตามรอบรถ | 2–3 ทำอัตโนมัติ: ระบบจัดเข้ารอบรถ ไม่ต้องให้ CS จัด **[ผมเลือก]** | ผ่าน SCDC แล้วไป CMG |
| Shop | CG Network, 4W Plaza (กทม.), Parcel | ไม่ข้าม · ใบแจ้งเก็บออกเฉพาะ 4W Plaza และ CG Network | 4W Plaza ตรงไป CMG · CG Network และ Parcel ผ่าน SCDC **[ผมเลือก]** |

## 6. หน้าจอ

**ใช้ร่วมทุก role**
- แถบบน: โลโก้ CRL, ช่องค้นหาเลขเดียว, ตัวสลับ role (แทน login)
- หน้ารายละเอียด RTV: เลข RTV ตัวใหญ่, แถบสถานะ 10 ขั้น (ขั้นที่ข้ามแสดงเป็นสีจาง), timeline (ใคร ทำอะไร เมื่อไร), ตารางเลขเอกสาร, รายการกล่อง, ปุ่ม "ขั้นถัดไป" ที่เปลี่ยนตาม role
- หน้ารายการงาน: กรองตามสถานะ ประเภท แบรนด์ และ "ค้างที่ฉัน"

**เฉพาะ role**
- Brand: ฟอร์มเปิดคำสั่ง (เลือกสาขา → ระบบเติมช่องทางให้), หน้าตอบยืนยันยอด
- CS: คิวงานรอจัดขนส่ง, ฟอร์มเลือกขนส่ง + วันนัด, ใบแจ้งเก็บ (พิมพ์ได้ มี QR ของเลข RTV)
- ขนส่ง: หน้ามือถือ รายการงานวันนี้, ปุ่มใหญ่ "เก็บแล้ว" / "เก็บไม่สำเร็จ"
- SCDC และคลัง CMG: หน้ารับสินค้า นับกล่อง, หน้าตรวจนับ (เฉพาะ CMG)
- Admin CN: คิวรอ CN แยกตามแบบ CN, ฟอร์มใส่เลข
- ผู้ดูภาพรวม: dashboard จำนวนงานต่อสถานะ, งานค้างตามผู้รับผิดชอบ, อายุงานเฉลี่ยต่อช่วง (เปิดคำสั่ง→เก็บ, เก็บ→CMG รับ, CMG รับ→CN)

**หน้าอธิบาย (ตอบโจทย์สิ่งส่งมอบ 3 ข้อ)**
1. **Flow ภาพรวม**: swimlane หน้าเดียว 7 role × 10 ขั้น คลิกแต่ละช่องเพื่ออ่านว่าใครทำอะไร มีตัวเลือกช่องทางเพื่อดูว่าขั้นไหนถูกข้าม
2. **Flow ละเอียด + walkthrough**: แต่ละขั้นมีคำอธิบาย ข้อมูลที่บันทึก เลขเอกสารที่เกิด และปุ่ม "เปิดหน้าจอนี้ในแอป"
3. **Demo นำชม**: เลือกเรื่อง แล้วกด "ถัดไป" ทีละขั้น ระบบสลับ role ให้เอง ไฮไลต์ปุ่มที่ต้องกด และมีคำบรรยายสั้นๆ ด้านข้าง กดย้อนหรือเริ่มใหม่ได้

## 7. เรื่องที่ใช้นำชม **[ผมเลือก]**

1. **Shop ปกติ กทม.** — Brand เปิด → CS จัด 4W Plaza + ใบแจ้งเก็บ → เก็บ → CMG รับ → ตรวจนับครบ → CN (แบบ MIM Shop)
2. **Consign Central ผ่าน SCDC** — Brand เปิด + RTV Note (ห้าง) → เข้ารอบ CG Network → SCDC รับและส่งต่อ → CMG รับ → ชิ้นไม่ครบ → Brand ยืนยัน → CN (แบบ E-tax Consign)
3. **Temp shop งาน Promotion** — CS จัด Parcel → ผ่าน SCDC → CMG → รอยืนยัน Promotion → CN (แบบ Temp Shop)
4. **เก็บไม่สำเร็จ** — ขนส่งแจ้งร้านปิด → CS นัดใหม่ → เก็บสำเร็จ

นอกจาก 4 เรื่องนี้ มีข้อมูลจำลองประมาณ 40 RTV กระจายทุกสถานะ เพื่อให้ dashboard และรายการงานดูสมจริง

## 9. วิธีสร้าง demo **[ผมเลือก]**

- Vite + React + TypeScript เป็นเว็บหน้าเดียว ไม่มี server ข้อมูลอยู่ในเบราว์เซอร์ (เริ่มจากไฟล์ข้อมูลจำลอง เก็บการเปลี่ยนแปลงใน localStorage มีปุ่ม "รีเซ็ตข้อมูล")
- แยกชั้นข้อมูลเป็น `api/` ที่มีฟังก์ชันรูปร่างเดียวกับ REST API ที่ระบบจริงจะมี (เช่น `createRtv`, `advanceStatus`, `searchByAnyNumber`) เพื่อให้ทีม dev เปลี่ยนเป็น backend จริงได้โดยไม่แก้หน้าจอ
- กฎ flow (ขั้นไหนข้าม, ใครทำขั้นไหนได้, แบบ CN) อยู่ในไฟล์ตั้งค่าไฟล์เดียว มี unit test (Vitest)
- Demo ใช้โดยผู้นำเสนอคนเดียวบนเบราว์เซอร์เดียว สลับ role เอง หน้าขนส่งแสดงในกรอบมือถือบนจอคอม ไม่รองรับหลายคนหลายเครื่องพร้อมกัน (ต้องมี server ซึ่งอยู่นอกขอบเขต)
- แต่ละ role มีตัวตนสมมติคงที่หนึ่งคน: Brand = แบรนด์ตัวอย่างหนึ่งแบรนด์ (เห็นเฉพาะงานแบรนด์นั้น), ขนส่ง = คนขับหนึ่งคนของ 4W Plaza และมีตัวเลือกเปลี่ยนเป็นคนขับ CG Network; role อื่นเห็นทุกงาน
- ลำดับการสร้าง: (1) กฎ flow + ข้อมูลจำลอง + หน้ารายละเอียด RTV และ timeline, (2) หน้าทำงานของทุก role, (3) Demo นำชม 4 เรื่อง, (4) หน้า Flow ภาพรวมและ Flow ละเอียด, (5) dashboard
- รันด้วย `npm run dev` และ build เป็นไฟล์ static เปิดจากโฟลเดอร์หรือวางบน web server ภายในได้
- ไม่ต่อยอดในโค้ดของ `CMG_Transport_DP` เพราะแอปนั้นกำลังเข้า UAT

## 10. ข้อเสนอสำหรับทีม dev (ระบบจริง) — คร่าวๆ

ทั้งหมดในข้อนี้เป็นข้อเสนอ ต้องยืนยันกับ IT ตาม governance policy ของ Central ก่อน

| ส่วน | ข้อเสนอ | เหตุผล |
|---|---|---|
| Frontend | Next.js (React + TypeScript), หน้าขนส่งเป็น mobile web / PWA | ตรงกับแอป pickup เดิม ใช้ component และธีมต่อได้ |
| Backend | API แยกชั้น (Next.js route handlers หรือ NestJS) + PostgreSQL | มี transaction; ตาราง event แบบเพิ่มอย่างเดียวสำหรับ track & trace |
| ยืนยันตัวตน | Microsoft Entra ID สำหรับพนักงาน; ขนส่งภายนอกใช้ลิงก์เปิดใช้งานต่อเครื่อง | แบบเดียวกับแอปเดิม |
| โครงสร้างข้อมูลหลัก | `rtv` (หัว), `rtv_box`, `rtv_document_ref` (ประเภท + เลข), `rtv_event` (สถานะ ผู้ทำ เวลา), master สาขา/แบรนด์/ขนส่ง | เลข RTV เป็นกุญแจหลัก เลขอื่นค้นย้อนได้ |
| เชื่อมระบบอื่น | ระยะแรกกรอกเลข SAP / FC ด้วยมือ; ระยะถัดไปรับไฟล์หรือ interface จาก Sprint FC และ SAP | ลดความเสี่ยงและเวลา |
| ที่ตั้งระบบ | Azure ของ Central (แอป + PostgreSQL), สำรองข้อมูลรายวัน | ตามที่แอปเดิมเตรียมไว้ |
| ต่อยอด | รวมแอป pickup เดิมเป็นโมดูลขั้น 2–8 | โค้ดและ test มีอยู่แล้ว |
